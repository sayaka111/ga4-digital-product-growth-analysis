# 技术实现与质量验证

本文件说明结果可靠性如何被验证。模型职责见[分析方法](methodology.md)，正式指标口径见[指标定义](metric_definitions.md)，检查结果与限制见[数据质量与分析限制](data_quality_and_limitations.md)。

## 1. 数据建模验证

SQL 按标准事件、核心事实和分析集市分层。每一层都以明确主键输出，并在进入下游前验证唯一性、行数关系和分子不超过分母。会话键同时包含设备用户与会话编号；用户首会话、用户日、留存明细、漏斗会话和订单事实分别保持独立粒度，避免连接后重复计数。

代表实现位于：

- `sql/models/staging/01_stg_ga4_events.sql`
- `sql/models/core/02_session_fact.sql` 至 `08_early_behavior_features.sql`
- `sql/analysis/09_acquisition_channel_quality.sql` 至 `20_channel_uncertainty.sql`

## 2. 指标治理验证

所有比率在输出中保留分子、分母、时间窗和实体粒度。特征窗口未成熟或结果窗口未成熟时使用 `NULL`，防止将“尚不可观察”误记为“未发生”。日历型指标与滚动时间窗口分别使用对应的日期和时间戳语义。

跨层一致性检查将获客、激活、留存、漏斗、生命周期和价值集市与 KPI 快照对账；看板只读取聚合结果文件，不在前端重新定义指标。

## 3. 订单与收入验证

订单检查先识别空值、空字符串和占位交易编号，再按用户、日期与有效交易编号聚合。对每个订单比较源记录数、不同非空收入值数、最小值和最大值，从而区分一致重复、收入未知与收入冲突。

跨日唯一性检查按“用户 + 有效交易编号”汇总不同日期数；占位编号单独检查收入和商品载荷，不进入有效订单结果。客单价对账同时验证收入分子与收入可识别订单分母，避免用全部订单或购买事件作分母。

## 4. 留存与漏斗质量控制

留存检查逐个日偏移验证观察资格，并确认未成熟结果为空。产品返回与核心行为返回分别计算，防止把任意活动当成核心价值复访。

漏斗先保存每个阶段的首次时间戳，再使用严格大于关系判断下一阶段。对相邻阶段时间戳相同的会话单独计数，确认其未被错误视为有序通过。日历月漏斗与获客同期群首会话漏斗分开构建，避免时期效应与用户批次效应混合。

## 5. SQL质量验证

三组检查分别覆盖：

- 基础事实：事件总量、用户与会话唯一性、订单收入分区和无效编号排除；
- 核心模型：首会话覆盖、用户日唯一性、留存行数、漏斗顺序和早期特征粒度；
- 分析集市：分母资格、结果层级、生命周期互斥、用户行数与固定窗口完整性。

检查脚本位于 `sql/tests/`，机器可读结果保存在 `data/*_test_results.json`。

## 6. Python统计验证

早期行为比较从 BigQuery 聚合计数读取发生组和未发生组，不传输用户级明细。统计输出包括组别发生率、Wilson 95%置信区间、风险差、风险比、优势比、双比例检验 p 值和 Benjamini–Hochberg 校正 q 值。

风险差用于表达绝对百分点变化，风险比和优势比补充相对强度；置信区间反映估计不确定性。渠道、月份和设备标准化用于检查可观测构成差异，但不被解释为因果识别。

## 7. 跨层一致性

完整验证链为：

```text
SQL事实模型 → 分析集市 → 聚合导出 → Python统计 → KPI快照 → 文档与看板
```

每个公开结果均能回溯到聚合 JSON/CSV 和对应 SQL。验证重点是实体粒度、窗口资格、结果层级与订单收入政策保持一致，而不是依赖人工复制数字。
